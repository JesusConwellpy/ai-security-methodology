## HIGH SEVERITY

### H-1: Frida root-detection bypass code has infinite recursion [banking-finance.md:195-207]

**File:** `/root/ai-security-methodology/industry/banking-finance.md`
**Lines:** 195-207
**Description:** The Frida script for Android root detection bypass overrides `File.exists()` but then calls `this.exists(path)` inside the override, which re-enters the overridden method. Java's `File.exists()` is zero-argument, and the override saves no reference to the original implementation. For any path NOT in the blocked list, this causes infinite recursion / stack overflow.

```javascript
// CURRENT (broken):
File.exists.implementation = function() {
    var path = this.getPath();
    var blocked = [...];
    if (blocked.indexOf(path) >= 0) return false;
    return this.exists(path);  // <-- re-enters overridden method, infinite loop
};
```

**Fix:** Save original method before overriding:
```javascript
var File = Java.use("java.io.File");
var existsOrig = File.exists.overload();
File.exists.implementation = function() {
    var path = this.getPath();
    var blocked = [...];
    if (blocked.indexOf(path) >= 0) return false;
    return existsOrig.call(this);  // call original (takes no args)
};
```

### H-2: vCenter SSO default password is factually wrong [default-credentials.md:394]

**File:** `/root/ai-security-methodology/dictionaries/default-credentials.md`
**Line:** 394
**Description:** Claims `administrator@vsphere.local` has default password `admin`. This is incorrect -- vCenter SSO password is set during deployment/installation, not a fixed default. The installer prompts the user to create this password. There is no universally known default.

**Fix:** Change to `Set during deployment` or remove the entry entirely. Alternatively, if referencing a specific vulnerable build, note the version range.

**Line:** 393

### L-7: compliance.md "Absolute Prohibitions" vs. pattern content tension

**Files:**
- `/root/ai-security-methodology/references/compliance.md` lines 7-33 (prohibitions)
- Multiple pattern files (authorization-bypass.md, business-logic-flaws.md, etc.)

**Description:** compliance.md lists "Unauthorized privilege escalation" and "Modifying production configurations" as absolute prohibitions. Meanwhile pattern files contain detailed, actionable instructions for exactly these actions (e.g., privilege escalation via response modification, mass assignment). This is the inherent tension between educational reference material and operational compliance rules. The documents do not explicitly bridge this gap -- there is no disclaimer at the top of pattern files stating "For authorized testing only."

**Fix:** Add a brief header to each pattern file clarifying that all techniques assume authorized testing scope. This prevents the perception of contradiction.
