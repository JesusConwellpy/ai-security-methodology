### BUG-2 [Critical] -- House of Botcake: `edit(a, p64(0))` only clears fd, NOT the tcache key (line 439)

The code does `edit(a, p64(0))` to clear the tcache key and bypass double-free detection. However, `p64(0)` is **8 bytes**, which only overwrites the first qword (`fd` at user_data + 0x00). The tcache key at **user_data + 0x08** is **NOT cleared**. The subsequent `free(a)` on line 445 will trigger the tcache double-free detection because the key field still contains the `tcache_perthread_struct` pointer.

This is contradicted by the Pitfalls section (line 490) which correctly states "Writing 0 to the start of user data overwrites both fd and key" -- the pitfalls comment assumes a 16-byte write, but the code does an 8-byte write.

**Fix**: Change `edit(a, p64(0))` to `edit(a, p64(0) * 2)` or `edit(a, p64(0) + p64(0))` to write 16 bytes, clearing both `fd` (offset 0) and the tcache key (offset 0x08).

### BUG-7 [Critical] -- ret2pt_regs: Stack offset calculation while-loop never executes (lines 569-574)

```c
while (idx * 8 < REG_IP)  // REG_IP = 0x60 = 96
```

After the ROP chain is built (buffer padding 8 + canary 1 + rbp 1 + 6 ROP entries = 16), `idx = 16`, `16 * 8 = 128`. Condition `128 < 96` is **FALSE**, so the while loop body never executes. The pt_regs fields (spawn_shell, cs, rflags, sp, ss) are written starting at `payload[16]` instead of the correct stack offset corresponding to the `pt_regs` region.

The root confusion: `REG_IP` (0x60) is the offset of RIP **within the pt_regs struct**, not the offset from the buffer to pt_regs on the kernel stack. The payload index does not map directly to stack offsets. Different kernel versions, compiler optimizations, and call depths produce different stack frame layouts.

**Fix**: Define a proper `BUFFER_TO_PTREGS_OFFSET` variable and use `while (idx * 8 < BUFFER_TO_PTREGS_OFFSET)` to pad, then write the 5 pt_regs values starting at `pt_regs.ip` (which is `BUFFER_TO_PTREGS_OFFSET + REG_IP`).

### BUG-8 [Critical] -- ret2pt_regs: Missing `iretq` gadget in the return-to-userland approach (lines 562-567)

The commented-out approach after the ROP chain:
```c
//   payload[idx++] = swapgs_ret + kaslr;
//   payload[idx++] = 0;               // padding  <-- should be iretq_gadget
//   payload[idx++] = 0;               // padding  <-- should NOT exist
//   // Then the iretq pops our forged pt_regs values from the stack
```

After `swapgs; ret`, the `ret` pops the next stack value as a jump target. Writing `0` there causes a crash. The correct sequence is: `swapgs; ret` pops `iretq_gadget` address -> executes `iretq` -> pops 5 values (RIP, CS, RFLAGS, RSP, SS). The two `0` padding entries displace the pt_regs data by 16 bytes, causing `iretq` to read wrong values.

Additionally, the non-commented code (lines 576-581) writes pt_regs values but **never places a `swapgs; ret` or `iretq` gadget on the stack at all**, so after `commit_creds` returns, execution jumps to `payload[16]` (spawn_shell address) in kernel mode -- which crashes with SMEP, or runs at ring 0 without proper return context.

**Fix**: Replace the two `0` padding entries with `iretq_gadget + kaslr`, making the sequence:
```c
payload[idx++] = swapgs_ret + kaslr;     // swapgs; ret
payload[idx++] = iretq_gadget + kaslr;   // iretq
// Then iretq pops the 5 values
```

### BUG-9 [Medium] -- msg_msg cross-cache: Wrong claim about leaked tty_struct magic (line 721)

The comment claims `leak[0]` (first qword of received message text) will contain the tty magic `0x5401`. However:

- msg_msg header occupies bytes 0x00-0x2F (48 bytes) of the kmalloc-1024 slab
- The user only receives mtext, which starts at slab offset 0x30
- tty_struct magic (0x5401) is at tty_struct offset 0x00 = slab offset 0x00, which is in the **msg_msg header area**, never visible to user-space
- `leak[0]` corresponds to slab offset 0x30 = tty_struct+0x30
- The kernel pointers that ARE leaked would be tty_struct fields at offset >= 0x30 (not magic or ops vtable)

**Fix**: Correct the comment to explain that tty magic is NOT visible to user-space. The leaked pointers would come from tty_struct fields at offsets >= 0x30 (e.g., `tty_struct->index`, `tty_struct->port`, or other later fields depending on kernel version).

### BUG-10 [Medium] -- ret2pt_regs: Alternative approach misrepresents execution path (lines 594-611)

The "Alternative approach: direct pt_regs overwrite without ROP" claims:

> 4. The function's natural return -> iretq -> spawn_shell as root

This is incorrect. A normal C function ends with `leave; ret`, not `iretq`. The `iretq` instruction only executes in the kernel's interrupt/exception return trampoline (e.g., `swapgs_restore_regs_and_return_to_usermode`). Overwriting `pt_regs.ip` and returning from the function does NOT trigger `iretq` -- it triggers `ret`, which pops a return address and jumps there, ignoring the pt_regs on the stack.

**Fix**: Clarify that the alternative approach requires the control flow to reach the kernel's `iretq` instruction (e.g., by corrupting the stack such that `ret` goes into a `swapgs; iretq` gadget). A bare overflow of pt_regs without reaching iretq simply gives a wrong return address.

### BUG-13 [Critical] -- SeBackup: PowerShell Add-Type missing class/namespace wrapper (lines 185-192)

```powershell
Add-Type -TypeDefinition @"
[DllImport("kernel32.dll", SetLastError=true, CharSet=CharSet.Unicode)]
public static extern IntPtr CreateFile(string name, uint access, uint share,
    IntPtr sec, uint creation, uint flags, IntPtr tmpl);
"@
$h = [Win32.NativeMethods]::CreateFile(...)
```

Two bugs:
1. `Add-Type -TypeDefinition` requires a **full class definition** with namespace/class wrapping. The bare `[DllImport]` on a method declaration without an enclosing class causes a PowerShell compilation error (`Missing type definition`).
2. The call uses `[Win32.NativeMethods]` but the Add-Type does not define a `NativeMethods` class or `Win32` namespace.

**Fix**:
```powershell
Add-Type -TypeDefinition @"
using System;
using System.Runtime.InteropServices;
public class NativeMethods {
    [DllImport("kernel32.dll", SetLastError=true, CharSet=CharSet.Unicode)]
    public static extern IntPtr CreateFile(string name, uint access, uint share,
        IntPtr sec, uint creation, uint flags, IntPtr tmpl);
}
"@
$h = [NativeMethods]::CreateFile(...)
```

### BUG-14 [Critical] -- SeTakeOwnership: `takeown /f` and `icacls` do not work on registry keys (lines 215-216)

```cmd
takeown /f "HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions"
icacls "HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions" /grant %USERNAME%:F
```

Both `takeown.exe` and `icacls.exe` operate on file system paths only (`C:\...`, `\\server\share\...`). Registry keys use `HKLM:\...` (PowerShell provider path) or `HKLM\...` (reg.exe path). Neither `takeown` nor `icacls` supports registry paths -- the commands will fail with "The system cannot find the file specified" or similar errors.

**Fix**: Replace with PowerShell registry ACL operations:
```powershell
$acl = Get-Acl "HKLM:\SOFTWARE\Microsoft\Windows Defender\Exclusions"
$rule = New-Object System.Security.AccessControl.RegistryAccessRule("$env:USERNAME","FullControl","Allow")
$acl.SetAccessRule($rule)
Set-Acl "HKLM:\SOFTWARE\Microsoft\Windows Defender\Exclusions" $acl
```
