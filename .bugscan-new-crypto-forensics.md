## BUG-1: CRITICAL — PRNG truncated LCG recovery: matrix is singular (missing target column)

**File:** `/root/ai-security-methodology/04-cryptography/prng/index.md`
**Lines:** 252–271
**Location:** `recover_truncated_lcg()` function

**Problem:** The lattice matrix is constructed as `(n+2) x (n+2)` but only columns `0..n` are assigned. Column `n+1` is implicitly zero (from the `matrix(ZZ, ...)` initialisation). This makes the matrix **singular** — every row has a zero in the last column. LLL on a singular matrix can find kernel vectors but will never recover hidden bits because the known truncated values (`truncated[]`) are never encoded in the lattice.

Additionally, the `+ c` term in the LCG recurrence `s_{n+1} = a*s_n + c mod m` is entirely ignored. The recurrence used in the lattice is just `a^(i+1)`, equivalent to `c = 0`.

**Fix:** The standard Hidden Number Problem (HNP) formulation for truncated LCG recovery requires a lattice that incorporates both the truncated outputs as constant offsets and the `+ c` term. One correct formulation:

```python
def recover_truncated_lcg(a, c, m, truncated, r):
    n = len(truncated) - 1
    P = 2**r  # hidden low-bit space
    B = matrix(ZZ, n + 2, n + 2)
    for i in range(n):
        B[i, i] = P                               # hidden low bits bounded by P
        B[i, n] = pow(a, i, m)                    # contribution to constraint
        B[i, n+1] = -(truncated[i] * P)            # known high-bit portion
    B[n, n] = m                                    # modulus constraint
    B[n, n+1] = sum(truncated[i] * pow(a, i, m) * P - ... )  # constant from c
    B[n+1, n] = 1
    B = B.LLL()
    ...
```

Or reference the known-good implementation in `lll-cryptanalysis` / `truncated_lcg.sage`.

**Severity:** High — code will not work as written.

## BUG-2: CRITICAL — Memory/minidump: stream directory reader reads 36 bytes instead of 12

**File:** `/root/ai-security-methodology/05-forensics/memory/index.md`
**Lines:** 358–367

**Problem:** Within the stream directory loop, `f.read(12)` is called **three times per iteration** instead of once. Each call advances the file pointer by 12 bytes:

```python
stype = struct.unpack_from("<I", f.read(12), 0)[0]  # reads bytes [pos, pos+12)
ssize = struct.unpack_from("<I", f.read(12), 4)[0]  # reads bytes [pos+12, pos+24) → WRONG
srva  = struct.unpack_from("<I", f.read(12), 8)[0]  # reads bytes [pos+24, pos+36) → WRONG
```

The offset parameters `0`, `4`, `8` are applied inside each 12-byte chunk, so:
- `stype` ← first 4 bytes of stream entry 1 (correct)
- `ssize` ← first 4 bytes of stream entry 2 (WRONG — should be bytes 4–7 of stream entry 1)
- `srva`  ← first 4 bytes of stream entry 3 (WRONG — should be bytes 8–11 of stream entry 1)

**Fix:** Read 12 bytes once into a variable:

```python
f.seek(stream_dir_rva)
for s in range(streams):
    entry = f.read(12)
    stype = struct.unpack_from("<I", entry, 0)[0]
    ssize = struct.unpack_from("<I", entry, 4)[0]
    srva  = struct.unpack_from("<I", entry, 8)[0]
    ...
```

**Severity:** High — all stream entries after the first are corrupted.

## BUG-3: HIGH — Disk/F2FS: NAT entry format is wrong (16 bytes vs real 9 bytes)

**File:** `/root/ai-security-methodology/05-forensics/disk/index.md`
**Lines:** 257–263

**Problem:** The NAT (Node Address Table) entry parsing reads 16 bytes per entry (stride of 16, two Q-sized fields). The actual F2FS NAT entry format is:

```
struct f2fs_nat_entry {
    __u8   version;      // 1 byte
    __le32 ino;          // 4 bytes
    __le32 block_addr;   // 4 bytes
} __packed;              // total: 9 bytes
```

The code reads `struct.unpack_from("<Q", nat_block, 8 + i * 16)` for inode number and `struct.unpack_from("<Q", nat_block, 8 + i * 16 + 8)` for block address — both using 64-bit little-endian (`Q`) when the actual fields are 32-bit each plus a version byte.

**Fix:** Use correct entry size and format:

```python
# F2FS NAT entry: 9 bytes packed (version + ino(32) + blkaddr(32))
entry_size = 9
nat_header_size = 8  # or 0 depending on F2FS version
for i in range(min(20, (len(nat_block) - nat_header_size) // entry_size)):
    entry_off = nat_header_size + i * entry_size
    version = nat_block[entry_off]
    ino = struct.unpack_from("<I", nat_block, entry_off + 1)[0]
    block_addr = struct.unpack_from("<I", nat_block, entry_off + 5)[0]
    if ino:
        print(f"Inode {ino} -> block {block_addr}")
```

**Severity:** High — NAT parsing will produce garbage inode/block values.

**File:** `/root/ai-security-methodology/05-forensics/disk/index.md`
**Line:** 250

**Problem:** `segment_count` is read from offset 40. The actual F2FS superblock layout puts `segment_count` at offset 24:

**Fix:** Change `struct.unpack_from("<I", sb, 40)[0]` to `struct.unpack_from("<I", sb, 24)[0]`.

**Severity:** High — reads wrong counter for total segment count.

```python
        pkt_data = f.read(incl_len)
        # Now parse Ethernet header (14 bytes) + IP header from pkt_data
```

**Severity:** High — will return false positives and misparse.

For `k = 7..11`, the attack will be attempted despite the text saying it should not work (Index Calculus in `GF(p^k)*` with `k >= 7` is typically infeasible for CTF-grade parameters).

## BUG-7: MEDIUM — RSA/Boneh-Durfee: `A = (N+1)//2` is inconsistent with variable mapping comment

**File:** `/root/ai-security-methodology/04-cryptography/rsa/index.md`
**Lines:** 207, 214–215

**Problem:** The polynomial is `f = x * (A + y) + 1` with `A = (N+1)//2`. The comment says the solution is `(x,y) = (d, phi(N) - (N+1))`. If `y = phi(N) - (N+1) = -(p+q)`, then `A + y = (N+1)//2 - (p+q)`. But `phi(N) = N + 1 - (p+q)`, so `A + y = phi(N) - (N+1)//2`, not `phi(N)`. The congruence `k*phi(N) + 1 ≡ 0 (mod e)` requires `A + y = phi(N)`, not `phi(N) - (N+1)//2`.

The correct standard formulation is:

```python
A = N + 1          # not (N+1)//2
f = x * (A + y) + 1  # f(k, -(p+q)) = k*phi(N) + 1 ≡ 0 (mod e)
```

where `x = k` (the coefficient from `ed = 1 + k*phi(N)`) and `y = -(p+q)`.

**Fix:** Either change to `A = N + 1` and update the shift bounds to match, or keep `A = (N+1)//2` with the correct variable mapping (e.g., `y = -p - q` not `y = phi(N) - (N+1)`).

**Severity:** Medium — the lattice may find incorrect short vectors without signalling failure.

## BUG-11: MEDIUM — PRNG/truncated LCG: `a^(i+1)` is XOR, not exponentiation, in pure Python

## BUG-12: LOW — Hash/custom: `find_arx_differential` has impractically slow brute-force

**File:** `/root/ai-security-methodology/04-cryptography/hash/index.md`
**Lines:** 192–203

**Problem:** The function iterates `delta_in` over `range(1, min(1 << 16, 1 << input_bits))` — up to 65535 values. For each, it runs `trials=2000` round function calls. That is up to **131 million** evaluations. Moreover, `output_diff` is a required parameter but in real differential cryptanalysis, it is the _unknown_ you are trying to find. The function loops over `delta_in` trying to find it, which is backwards (you choose `delta_in`, measure `output_diff`).

**Fix:** Restructure to accept `delta_in` and estimate `P(output_diff | delta_in)`, or add a note that this is illustrative only and not intended for production use.

**Severity:** Low — reference code that is too slow for practical use.
