## CRITICAL GAPS

### CG-1. SSRF IMDSv2: Bypass Table Contradicts Itself
**File:** `/root/ai-security-methodology/01-web-attacks/ssrf/index.md`
**Lines:** 291 vs 318
**Severity:** CRITICAL GAP
**What's wrong:** The Bypass table (line 291) lists "IMDSv2 -> DNS rebinding, try IMDSv1, use gopher..." but Pitfalls (line 318) correctly states "IMDSv2 blocks v1 on modern AWS. Do not assume v1 works." The bypass table suggests trying v1 even though v2 explicitly disables v1. Worse, this is a self-contradiction within the SAME document.
**What's missing:** The bypass table must NOT list "try IMDSv1" as a viable bypass when v2 is enforced. IMDSv1 is either available or not -- there is no "try it anyway" scenario that works.
**Suggested fix:** Remove "try IMDSv1" from the IMDSv2 bypass row. Replace with: "IMDSv2 block is intended to be robust. DNS rebinding with PUT-token header is the only bypass path."

### CG-2. php://input Prerequisite Missing (Both Docs)
**File:** `/root/ai-security-methodology/01-web-attacks/path-traversal/index.md` (line 192) and `/root/ai-security-methodology/payloads/web/index.md` (lines 542-544)
**Severity:** CRITICAL GAP
**What's wrong:** Both documents present `php://input` as a working LFI-to-RCE technique without stating the critical prerequisite: `allow_url_include=On` in php.ini. In modern PHP (5.2+), this is `Off` by default. Anyone following this doc to test a target will waste hours on a technique that has effectively zero success rate unless the target has explicitly enabled it.
**What's missing:** A mandatory prereq note: "Requires `allow_url_include=On` in php.ini. This defaults to Off since PHP 5.2 and is almost never enabled in production. Before using this technique, verify via `phpinfo()` leak or error message."
**Suggested fix:** Add the prerequisite as a WARNING block immediately before every `php://input` example.

### CG-3. WebSocket CSWSH Missing Authentication Prerequisite
**File:** `/root/ai-security-methodology/payloads/web/index.md` (lines 1336-1353)
**Severity:** CRITICAL GAP
**What's wrong:** The Cross-Site WebSocket Hijacking technique shows JS code that connects to a WebSocket endpoint, but never states the prerequisite: the WebSocket endpoint must authenticate via browser cookies. If the endpoint uses Authorization headers, bearer tokens, or handshake-specific authentication, CSWSH cannot steal the connection.
**What's missing:** Prerequisite note: "This attack only works when the WebSocket server authenticates via cookies that the browser automatically sends. Token-based auth via `Sec-WebSocket-Protocol` or handshake query params is not affected."
**Suggested fix:** Add a prerequisite paragraph at the start of the WebSocket Attacks section.

### CG-4. `$where` NoSQL Injection Marked as Viable but Disabled by Default
**File:** `/root/ai-security-methodology/01-web-attacks/nosql-injection/index.md` (lines 129-168)
**Severity:** CRITICAL GAP
**What's wrong:** The doc dedicates 40 lines to `$where` injection techniques and timing-based extraction. However, Pitfall note (line 235) mentions `$where` is "disabled by default in Mongoose 7+". This is buried at the end. `$where` was deprecated in MongoDB 3.6 and disabled by default in Mongoose 7 (released 2022). A tester following the doc in sequence reaches `$where` as a primary technique and may waste significant time.
**What's missing:** The Decision Tree (line 27-31) should mention the `$where` availability check as an early step. The technique section should start with a prominent note about modern Mongoose/MongoDB versions.
**Suggested fix:** Add a red prereq box at the top of the `$where` technique: "Only works on Mongoose < 7 or when explicitly enabled. Default is disabled. Test with `$regex` first."

### H-5. SSTI `|attr()` Bypass Misleading for SandboxedEnvironment
**File:** `/root/ai-security-methodology/01-web-attacks/ssti/index.md` (lines 207-208)
**Severity:** HIGH
**What's wrong:** The Bypass section presents `|attr('__cla'+'ss__')` as a way to bypass filters. However, in Jinja2's `SandboxedEnvironment`, `|attr()` does NOT bypass `__` attribute restrictions. The sandbox blocks double-underscore attributes at the `getattr` level regardless of how the attribute name is constructed. A tester who follows this and hits a SandboxedEnvironment will get an `SecurityError` and not understand why.
**What's missing:** A caveat: "`|attr()` bypasses string-level keyword filters but does NOT bypass Jinja2's `SandboxedEnvironment`. If the response is a `SecurityError`, the target uses `SandboxedEnvironment` and you need `lipsum`, `cycler`, or `joiner` globals."
**Suggested fix:** Add at line 207: "NOTE: SandboxedEnvironment blocks `__` attributes at the getattr level. `|attr()` will NOT bypass it."

### H-6. JWT `alg: none` Listed Without Modern Library Context

**Suggested fix:** Add at line 36: "Only works against libraries < 2018 (jsonwebtoken < 9, PyJWT < 2, jose < 4) or servers with `allowInsecureAlgorithms: true`. Modern libraries reject `alg: none` at the parser level."

### H-9. Image Polyglot Limitation Understated (Nearly Dead Technique)
**File:** `/root/ai-security-methodology/01-web-attacks/file-upload/index.md` (line 285)

### H-10. Unanchored Regex Example Logical Chain Incomplete
**File:** `/root/ai-security-methodology/01-web-attacks/command-injection/index.md` (lines 287-290)
**Severity:** HIGH
**What's wrong:** The example shows `preg_match('/^(\d{1,3}\.){3}\d{1,3}/', $_GET['ip'])` and claims the bypass `1.1.1.1;cat /flag.txt` works. But `preg_match` WILL return 1 (true) because the pattern matches the PREFIX. The vulnerability chain is: `preg_match` returns 1 (match found) -> the `if(preg_match(...))` check passes -> the code trusts `$_GET['ip']` and passes it to `exec()`. The doc does not explain this logical chain, making it look like `preg_match` is failing when it's actually succeeding at matching the prefix.
**What's missing:** An explanation: "`preg_match` succeeds (returns 1) because the pattern matches the prefix `1.1.1.1`. The code then uses the ORIGINAL input `$_GET['ip']` (including the suffix) unsafely in a shell command."
**Suggested fix:** Add: "Key insight: `preg_match()` returns 1, not 0. The check 'passes' because a valid IP prefix is present, but the full input (including `;cat /flag.txt`) is used in the shell call."
